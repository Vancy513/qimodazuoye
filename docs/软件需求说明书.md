# 软件需求说明书

**项目名称**：联动实验室（SmartDorm Lab）
**选题**：主题三 —— 联动实验室 · 智能宿舍自动化规则编排 App
**课程**：《鸿蒙高级应用开发工程师认证》
**开发形式**：独立完成（1 人）
**文档版本**：v1.0（2026-11-13）

---

## 1. 项目概述

### 1.1 背景

智能宿舍的常见形态是「用手机遥控设备」，但真正减少操作负担的是**自动化联动**：
宿舍无人时自动熄灯，闷热时自动开空调，潮湿时自动关窗。这类需求本质上是
「条件 → 动作」的规则编排，规则之间还会互相冲突（一条规则要开灯，另一条要熄灯）。

本项目面向宿舍场景，提供一个**可视化规则编排 + Mock 环境验证**的工具：
用户编辑规则、调整模拟环境、观察联动结果与执行顺序，并能在冲突发生时看到明确的裁决结果。

### 1.2 目标

| 编号 | 目标 | 验收方式 |
| --- | --- | --- |
| G1 | 支持 4 类设备、4 项环境数据的完整联动闭环 | 手动操作 + 截图 |
| G2 | 规则可增删改启停，含双条件规则 | 规则库页面操作 |
| G3 | 规则引擎按实际输入求值，输出可追溯的执行顺序 | 执行日志「执行顺序」 |
| G4 | 冲突有确定的处理策略且可解释 | 日志「冲突处理」+ 单元测试 TC-06 |
| G5 | 数据持久化，杀进程重开可恢复 | 强制停止后重启对比 |
| G6 | 至少 6 条覆盖正常/边界/异常的自动化测试 | 10 条本地单元测试 |

### 1.3 范围

**包含**：规则编辑、环境模拟、设备控制、联动执行、日志追溯、场景演练、本地持久化、单元测试。

**不包含**：真实硬件对接、云平台、账号体系、3D 空间建模、AI 生成规则。
（课程要求明确不要求真实硬件与云平台，Mock 环境即为验收环境。）

## 2. 用户与使用场景

### 2.1 目标用户

- **宿舍学生**：希望「回到宿舍灯已经亮着、湿度大时窗帘自动关上」。
- **课程评阅者**：需要在一个界面上快速验证规则引擎是否正确、冲突是否可解释。

### 2.2 典型场景

| 场景 | 用户操作 | 期望结果 |
| --- | --- | --- |
| S1 夏日午后回宿舍 | 选「夏日午后」场景 → 应用 | 空调开启 24℃、加湿器开启、灯开启，日志显示命中 3 条规则 |
| S2 深夜熄灯 | 人员切到「无人」→ 运行联动 | 灯关闭；「昏暗开灯」被「无人熄灯」压制并记入冲突 |
| S3 回南天关窗 | 湿度拖到 88 → 运行联动 | 窗帘关闭，无其他设备动作 |
| S4 自定义规则 | 新建「温度低于 18 且有人 → 开空调制热」 | 保存后出现在规则库，调低温度后可触发 |
| S5 恢复进度 | 编辑若干规则 → 杀进程 → 重新打开 | 规则、设备、日志全部恢复 |

## 3. 功能需求

### 3.1 功能结构

```text
联动实验室
├── 控制台
│   ├── 环境模拟（温度/湿度/光照/人员）
│   ├── 设备控制（灯/空调/窗帘/加湿器：开关 + 档位）
│   ├── 运行联动
│   └── 最近一次执行摘要
├── 规则库
│   ├── 规则列表（条件→动作摘要、优先级、启停）
│   ├── 新建 / 编辑（名称、优先级、1~2 条件、1~2 动作）
│   └── 删除
├── 执行日志
│   ├── 记录列表（时间、命中规则数、摘要）
│   └── 展开详情（环境快照、执行顺序、冲突处理）
└── 场景演练
    ├── 5 组预设场景（应用即执行）
    ├── 冲突策略说明
    └── 恢复默认数据
```

### 3.2 用例说明

| 用例 | 前置条件 | 主流程 | 异常流 |
| --- | --- | --- | --- |
| UC-01 调整环境 | 应用启动 | 拖动滑块 / 切换人员 → 顶部命中数刷新 → 写入 Preferences | 存储失败：顶部提示，数据仍在内存生效 |
| UC-02 控制设备 | 应用启动 | 点开关 / 拖档位 → 卡片边框与文案变化 → 持久化 | 同上 |
| UC-03 运行联动 | 至少 1 条启用规则 | 点「运行联动」→ 引擎求值 → 设备状态更新 → 生成日志 → Toast 摘要 | 无规则命中：提示「没有规则命中，设备保持原状」 |
| UC-04 新建规则 | 规则库页 | 点「新建规则」→ 填写 → 保存 → 校验通过 → 入列表 | 校验失败：编辑器红字提示，不关闭 |
| UC-05 编辑规则 | 已有规则 | 点「编辑」→ 修改 → 保存 | 同上 |
| UC-06 启停规则 | 已有规则 | 点开关 → 立即生效并持久化 | — |
| UC-07 删除规则 | 已有规则 | 点「删除」→ 从列表移除 → 持久化 | — |
| UC-08 查看日志 | 至少 1 条日志 | 点「详情」→ 展开执行顺序与冲突 | 无日志：空状态提示 |
| UC-09 场景演练 | 应用启动 | 点「应用」→ 写入环境 → 立即执行一次联动 | — |
| UC-10 重启恢复 | 曾产生数据 | 杀进程 → 重新打开 → 读取 Preferences → 恢复 | 数据损坏：捕获异常并回落默认值 |

### 3.3 界面需求

| 页面 | 关键元素 | 交互反馈 |
| --- | --- | --- |
| 控制台 | 环境卡片、设备卡片（2×2）、运行按钮、最近执行 | 滑块跟手、开关状态色、命中数实时变化 |
| 规则库 | 规则卡片、双条件标签、启停开关、新建按钮 | 停用规则整体降透明度 |
| 日志 | 时间、规则数、展开详情、冲突高亮 | 点击展开/收起 |
| 场景 | 场景卡片、环境标签、应用按钮 | 应用后 Toast 显示执行摘要 |
| 规则编辑器 | 名称输入、优先级、条件区、动作区、保存/取消 | 校验失败红字提示；遮罩层浮于页面之上 |

## 4. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 单次联动（≤20 条规则）计算耗时 < 5ms；页面滚动无明显掉帧 |
| 可靠性 | Preferences 读写均有 try/catch，单点失败不导致崩溃，回落默认数据 |
| 可维护性 | model / engine 不依赖 @ohos，可独立测试；UI 只做展示与状态持有 |
| 可测试性 | 引擎为纯函数，输入输出均为值对象，便于 Mock |
| 兼容性 | 适配 Phone，API 17；深色模式下使用固定色板，不依赖系统主题 |

## 5. 数据模型

### 5.1 实体

| 实体 | 字段 | 说明 |
| --- | --- | --- |
| EnvState | temp, humidity, light, occupancy | 环境快照，occupancy 用 0/1 表示无人/有人 |
| DeviceState | id, name, type, power, value, unit, min, max | 设备状态与可调范围 |
| RuleCondition | key, op, value | 环境键 + 比较符 + 阈值 |
| RuleAction | deviceId, power, value | 目标设备与目标状态 |
| AutomationRule | id, name, enabled, priority, conditions[], actions[] | 规则，条件取「与」 |
| TriggerRecord | id, time, env, matchedRules[], steps[], changes[], conflicts[], note | 一次执行的完整快照 |
| ScenePreset | id, name, desc, env | 环境场景预设 |

### 5.2 设备定义

| 设备 | id | 类型 | 数值含义 | 范围 |
| --- | --- | --- | --- | --- |
| 吸顶灯 | dev_light | light | 亮度 % | 0~100 |
| 空调 | dev_ac | ac | 目标温度 ℃ | 16~30 |
| 窗帘 | dev_curtain | curtain | 开合 % | 0~100 |
| 加湿器 | dev_humidifier | humidifier | 湿度 % | 0~100 |

### 5.3 预置规则

| 规则 | 条件 | 动作 | 优先级 |
| --- | --- | --- | --- |
| 高温开空调 | 温度 > 28 | 空调 ON 24℃ | 3 |
| 昏暗开灯 | 光照 < 30 **且** 有人 | 灯 ON 70% | 4 |
| 无人熄灯 | 无人 | 灯 OFF | 5 |
| 无人省电关空调 | 无人 | 空调 OFF | 5 |
| 干燥加湿 | 湿度 < 40 | 加湿器 ON 60% | 2 |
| 潮湿关窗 | 湿度 > 80 | 窗帘 OFF | 3 |

> 「高温开空调」(P3) 与「无人省电关空调」(P5) 在「30℃ 且房间无人」时构成真实冲突，用于演示优先级裁决：
> 前者要把空调开到 24℃，后者要关掉空调，最终 P5 生效、P3 被记入冲突记录。
> 「昏暗开灯」要求有人、「无人熄灯」要求无人，两者条件互斥，正常不会相互压制。

## 6. 模块划分与接口

| 模块 | 文件 | 职责 | 对外接口 |
| --- | --- | --- | --- |
| 领域模型 | model/LabTypes.ets | 数据结构、常量、深拷贝与格式化辅助 | 类型定义、cloneEnv/cloneDevice/cloneRule/readEnv |
| 规则引擎 | engine/RuleEngine.ets | 条件求值、排序、执行、冲突裁决、校验 | runRules / evaluateRule / validateRule / countMatchedRules / formatRuleSummary |
| 数据层 | data/LabRepository.ets | Preferences 初始化、读写、清空 | init / read / write / clearAll |
| Mock 数据 | data/LabDefaults.ets | 默认设备、规则、场景 | createDefaultDevices / Env / Rules / Scenes |
| 表现层 | pages/Index.ets | 四个工作区、状态持有、持久化调度 | 无（@Entry 页面） |

### 6.1 关键接口签名

| 接口 | 输入 | 输出 | 异常/边界 |
| --- | --- | --- | --- |
| runRules | rules, devices, env, now, recordId | ExecutionResult{record, devices, changed} | 不修改入参；设备不存在跳过；冲突记录 |
| evaluateRule | rule, env | boolean | enabled=false 或条件为空返回 false |
| validateRule | rule, devices | string[] | 空数组表示通过；返回全部错误 |
| countMatchedRules | rules, env | number | 用于界面实时提示 |
| LabRepository.init | UIAbilityContext | boolean | 失败返回 false，界面降级 |

## 7. 异常与边界设计

| 编号 | 情况 | 处理 |
| --- | --- | --- |
| E1 | 规则名为空 / 条件为空 / 动作为空 | 保存前拦截，编辑器提示 |
| E2 | 动作数值超出设备范围 | 引擎 clamp 到边界；校验时提示越界 |
| E3 | 规则引用不存在的设备 | 执行时跳过该动作；校验时报错 |
| E4 | 两条规则控制同一设备且目标不同 | 高优先级生效，低优先级记入冲突 |
| E5 | 停用规则 | 不参与求值 |
| E6 | Preferences 读到的 JSON 损坏 | try/catch 回落默认数据并提示 |
| E7 | 日志无限增长 | 最多保留 30 条，超出丢弃最旧 |
| E8 | 无规则命中 | 设备不变，日志 note 说明原因 |

- **单元测试**：规则引擎与校验逻辑，使用 @ohos/hypium 本地单元测试，10 条用例覆盖正常 / 边界 / 异常。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 规则条件组合爆炸 | 界面复杂 | 限制 1~2 个条件、1~2 个动作，保持可解释 |
| 冲突策略不直观 | 评阅者质疑 | 日志显式记录「谁压制谁」，单元测试固定行为 |
| Preferences 容量 | 数据丢失 | 只存必要字段，日志上限 30 条 |
| 模拟器不可用 | 无法演示 | 支持真机运行，API 17 通用 |
